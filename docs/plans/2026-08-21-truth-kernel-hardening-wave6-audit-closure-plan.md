## P0-A — Stale `Reconciled` can revive over a live `Degraded` snapshot

**Root cause** (`crates/calm-core/src/authority/snapshot.rs:197-209`): `compute_with_recorded_freshness` runs `compute()` (which includes the `live_mtime_drift` check — the ONLY signal that catches "disk changed, DB not reindexed yet") and then unconditionally looks up a prior recorded snapshot by `snapshot_id`. Because `snapshot_id` is a digest over `file_index` DB rows only (`source_catalog_digest`, snapshot.rs:335-348), a live-disk-only change leaves `snapshot_id` unchanged — so the lookup hits a stale `Reconciled` record and overwrites the just-computed `Degraded` right back to `Reconciled`. This is called from `mint_review_authority_for_edit_context` (guardrails.rs:1276), so the authority minted for `edit_context` can carry a falsely-strong freshness class. At spend time (`edit.rs:1436`), only `.snapshot_id` is checked — freshness is never re-derived — so the false guarantee survives all the way to the write.

**Fix:**
1. In `compute_with_recorded_freshness`, only consult the recorded-snapshot table when THIS call's own `live_mtime_drift` did not just fire. Never let a stale recorded class override a live-detected drift from the same call:
   ```rust
   pub fn compute_with_recorded_freshness(conn, project_root, state_conn) -> rusqlite::Result<Self> {
       let catalog = InputCatalog::for_project(project_root);
       let drift = index_input_drift(conn, &catalog)?;
       let mut freshness_class = drift_to_freshness(drift);
       let live_drifted = freshness_class == FreshnessClass::Current
           && live_mtime_drift(conn, project_root)?;
       if live_drifted {
           freshness_class = FreshnessClass::Degraded;
       }
       let mut snapshot = Self::build(conn, project_root, freshness_class)?;
       if !live_drifted
           && let Some(recorded) = Self::load(state_conn, &snapshot.snapshot_id)?
           && recorded.freshness_class > snapshot.freshness_class
       {
           snapshot.freshness_class = recorded.freshness_class;
       }
       Ok(snapshot)
   }
   ```
2. At spend time (`edit.rs:~1436`), stop discarding freshness. Recompute via `compute_with_recorded_freshness` (post-fix-1) and re-check `meets_bar_for(required_approver_class)` the same way mint time does — refuse the spend with a new `SNAPSHOT_FRESHNESS_DEGRADED_SINCE_MINT` error if it no longer clears the bar, instead of trusting a bare `snapshot_id` string match.
3. Extend `live_mtime_drift` to also catch **new, not-yet-indexed** files, not just changed/deleted ones already in `file_index` (currently `SELECT path, mtime FROM file_index` never sees a brand-new file). Cheapest correct fix: compare `collect_source_files()`'s live count/set against `file_index`'s row count for the same root; a set mismatch is drift. Full path-set comparison is more correct than a count if the false-negative rate (add+delete same tick) matters — worth a follow-up decision, not blocking P0-A.
4. New test: reproduce the exact scenario the current "falls back to live drift" test doesn't cover — record a `Reconciled` snapshot, then mutate a file ON DISK ONLY (not through the indexer, so `file_index` stays untouched and `snapshot_id` stays identical), then assert `compute_with_recorded_freshness` still reports `Degraded`, and that `mint_review_authority_for_edit_context` refuses to mint (or mints at a lower tier) as a result.

## P0-B — TOCTOU between live-verification and the read that serves it

**Root cause:** `verify_live` (outcome.rs:680-747) reads the file once to verify identity and (on a changed file) re-derive `line_start`/`line_end`. Every caller of `resolve_symbol` then does ITS OWN separate `std::fs::read_to_string` to actually serve content (`inspect.rs:253` for `source()`; `understand()` at inspect.rs:620 has the identical pattern). Nothing pins these two reads to the same file generation — a write landing between them serves content that was never actually verified against the resolved range.

**Fix:**
1. Introduce `ResolvedLiveTarget { candidate: CandidateRow, bytes: String, content_hash: String }`. Change `verify_live`'s fast path (hash matches `file_index`) to still return the bytes it already had to read to compute that hash (currently discarded), and the slow path (re-parse) to return the bytes it re-parsed from. `resolve_symbol` propagates this through `SymbolResolution::Found`.
2. Change every consumer (`source()`, `understand()`, and the edit-path's `best_live_range` equivalent) to slice from the propagated bytes instead of re-reading the file. One read, one identity, one set of bytes from verification to output — matches the pattern the P0-1 Wave-1 work already established for verification itself, just extended one hop further to serving.
3. Keep a fresh read immediately before any WRITE (edit_lines/edit_symbol already re-validate via `expected_hash`) — this fix is about read-path consistency, not weakening the existing write-time hash guard.
4. Residuals to close alongside this (small, same area):
   - `verify_live`'s "no `file_index` row → trust DB row as-is" (outcome.rs:692-697) should attempt a live read anyway before giving up — a missing `file_index` row doesn't mean the file itself is unreadable.
   - Candidates above `MAX_LIVE_VERIFIED_CANDIDATES` (20) currently skip live-verification entirely (outcome.rs:652-654) — at minimum, verify the top N by some cheap tiebreak (e.g. most-recently-touched file) rather than silently trusting all 20+ as unverified `Ambiguous`.
   - `hash_content`'s FNV-1a 64-bit (discovery.rs:102-111) is fine for change-detection but is not collision-resistant; not urgent to change (no adversarial threat model here), but worth a one-line doc caveat if `ResolvedLiveTarget`'s `content_hash` is ever exposed as an integrity claim rather than an internal cache key.

## P0-C — Confidence-tier consumers: fix the two real fail-opens, leave the deliberate one

Three `.unwrap_or` sites, two of which are real bugs and one of which is an intentional, already-documented safety choice — worth **not** conflating them:

1. `weakest_route_confidence` (trace.rs:1018-1026): `.unwrap_or(EdgeConfidence::Formal)` when NO step's confidence parses. Defaulting the *weakest*-route calculation to the *strongest* possible tier on missing data is backwards. **Fix:** `.unwrap_or(EdgeConfidence::Unresolved)`.
2. `path()`'s `certain` flag (trace.rs:1129-1134): `.unwrap_or(true)` on an unparseable confidence string. `certain` is meant to mean "backed by Formal/Resolved only" — an unparseable string should fail closed. **Fix:** `.unwrap_or(false)`.
3. `coreness.rs:51-53`'s `is_confirmed = ...unwrap_or(true)` is **not** a bug to flip — it's the stricter/safety graph, and failing an unrecognized confidence string INTO "confirmed" is the conservative direction for a hub-detection false-negative guard. Leave as-is; note it explicitly in code so the next audit doesn't re-flag it.
4. Wire the already-computed-but-unread `verified_caller_count` (schema.rs:179, populated by `refresh_caller_counts`, graph.rs:388-404) into at least one real consumer: surface a `verified_caller_count`/`caller_count` split in `edit_context`'s risk reasons and `callers()`'s output, so an agent can tell "14 callers, 3 verified" apart from "14 callers, 0 verified" — the exact distinction the audit's P0-3 class of findings traces back to. This is the one item in this plan that's purely additive (new signal surfaced, nothing tightened), safe to do independently of 1-3.

## P1-A — Retrieval: close the default-hybrid body-search gap and the false-confidence floor

1. `search_hybrid`'s lexical leg calls `search_symbol` (search.rs:1112), not the body-aware `search_text`. When the embedder is unavailable, hybrid degrades to name/docstring/signature only — body content becomes literally unreachable from the default search path. **Fix:** degrade to `search_text` (already merges chunk-body FTS, search.rs:365-450) instead of `search_symbol` on the no-embedder branch; when the embedder IS available, `chunk_semantic_results` already covers bodies, so the gap is specifically the degraded path.
2. `understand()`'s `resolution_confidence == "confident"` (inspect.rs:521-529) has no absolute floor — a `top.score` of 0.001 with no second candidate is still "confident". **Fix:** add `MIN_CONFIDENT_SCORE` alongside `UNDERSTAND_AMBIGUOUS_MARGIN_RATIO`; require `top.score >= MIN_CONFIDENT_SCORE` for `"confident"`, else `"weak"` (new third tier, not `"ambiguous"` — there's no second candidate to disambiguate against).
3. `parse_understand_kind`'s silent fallback to `Symbol` on an unrecognized string (inspect.rs:739-746) should at minimum surface a `note` in the output ("unrecognized kind '<x>', defaulting to symbol") — currently indistinguishable from a deliberate default.
